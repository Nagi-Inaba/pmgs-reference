## 結論

PMGS Reference v0.5.0は、同じ固定artifactを[PyPI](https://pypi.org/project/pmgs-reference/0.5.0/)と[GitHub Release](https://github.com/Nagi-Inaba/pmgs-reference/releases/tag/v0.5.0)へ公開した。両配布面のwheelとsdistは、ファイル名、bytes、SHA-256が一致した。

公開済みwheelを空の専用`uv tool`環境へ導入し、version表示、合成fixtureの初回setup、再実行、doctor、FI lookupに合格した。PMGS原本、生成SQLite、全量exportは配布していない。

## Tagとrelease workflow

`v0.5.0`は`main`のcommit `65a33f5628e380fdbeb78d26570b3b9d5ccfbb35`を指し、`pyproject.toml`のversion `0.5.0`と一致した。

Release workflowは次のgateに合格した。

- repository boundaryとversion・tag契約
- 一度だけ構築したwheelとsdistのmetadata・hash検査
- Linux、Windows、macOSでのsource test、wheel導入、sdist由来wheel導入
- 3 OSの合成fixture決定性比較
- Cloudflare Worker、WebMCP、npm audit

`pypi` environmentのrequired reviewer承認後、Trusted Publishingとdigital attestationを使ってPyPIへ公開した。PyPI成功後、同じworkflow artifactからGitHub Releaseを作成した。

## 残る境界

- PyPI v0.5.0のlong descriptionはtag時点の`README.md`を固定しているため、公開前の事実に合わせたrelease candidate表記を含む。PyPI上の既存version metadataは同じversionへ上書きできないため、repositoryの`main`だけを公開後の状態へ更新する。
- Claude Codeの設定、登録、skill導入は自動検証済みだが、実モデルによるlive MCP評価は`not_observed`のままである。
- 旧SQLite向けFTS5 fallbackは合成fixtureで検証済みだが、全量JPPMでの所要時間と一時disk使用量はIssue #56で追跡する。
- R2 upload、Worker deploy、独自domain、外部検索indexは実施していない。Python packageの公開成功をWeb公開成功として扱わない。
